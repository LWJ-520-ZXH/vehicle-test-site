# 车载测试学堂 · 后端内容中台方案 · 企业级评审

> **文档级别**：方案评审（Design Review）
> **评审视角**：企业级标准（安全 / 可靠 / 合规 / 可观测 / 可运维）

## 0. 总体结论

方案架构选型合理（Cloudflare 原生产栈、密码less 鉴权、内容门禁分层），**安全基线优于多数自建方案**。但作为企业级系统，当前稿在 **CSRF 防护、数据持久化(DR)、会话吊销、PII 合规、可观测性、测试策略** 六个方面存在缺口，需补足后方可投产。

## 1. 方案优势（应予保留）

- 密码less 架构：无密码库，天然规避撞库/明文泄露。
- 静态仅放元数据、正文一律门禁：匿名无法从 JS 扒内容。
- 全站统一 Cloudflare 安全底座（WAF/DDoS/HTTPS）。
- 审批模型极简（单 `approved` 字段），无后台运维负担。

## 2. P0 — 致命缺口（投产前必改）

### P0-1 · CSRF / 凭据型 CORS 配置缺失
**问题**：方案用 `HttpOnly` JWT cookie + `credentials: include` 调 POST 接口（`/api/apply`、`/api/auth/register`）。文档只说"CORS 收敛到自有域名"，未定义 `Access-Control-Allow-Credentials` 与防 CSRF 机制。若 `Allow-Origin` 误配为 `*`，cookie 凭据会失效；且跨站 `fetch` 仍可能触发状态变更。
**影响**：账户冒用、伪造申请。
**建议**：
- `Access-Control-Allow-Origin` 必须为**显式域名**（非 `*`），并配套 `Access-Control-Allow-Credentials: true`。
- 所有状态变更 POST 增加**自定义请求头校验**（如 `X-Requested-With: fetch` 或随机 nonce）——浏览器跨站 `fetch` 不会自动附加该头，构成 CSRF 防线。
- cookie 设 `SameSite=Strict`（或至少 `Lax` + 头校验双保险）。

### P0-2 · D1 无备份与灾难恢复(DR)策略
**问题**：`users` / `applications` 表仅存于 D1，文档未提备份。Cloudflare D1 默认不自动备份（需手动 export）。若 D1 数据损坏/误删，用户与申请记录**不可恢复**（内容可从 Git 重建，但账号体系丢失）。
**影响**：单点数据丢失 → 全站登录/审批瘫痪。
**建议**：
- 定时任务（cron Worker 或 CI）执行 `wrangler d1 export` 落地到 R2 / 私有 Git。
- 明确 RTO（恢复目标）< 4h、RPO（数据丢失窗口）< 24h。
- 内容表以 **Git JSON 为唯一真源**，D1 视为派生缓存，重迁脚本幂等可重跑。

### P0-3 · 账户枚举与邮件轰炸风险
**问题**：`/api/auth/register` 与 `/api/auth/login` 对"邮箱是否已注册"返回可区分响应，且任意人可对任意邮箱触发魔法链接邮件。
**影响**：① 枚举哪些邮箱已注册；② 攻击者用站长邮箱高频触发，导致发信域名进黑名单(SPF 劣化)。
**建议**：
- 注册/登录**统一返回同一文案**（"若邮箱有效，链接已发送"），不区分存在与否。
- 按 **邮箱 + IP** 双维度限流（如每邮箱 5 次/10 分钟，每 IP 20 次/小时）。
- 连续失败达阈值引入人机校验（turnstile）。

### P0-4 · 魔法链接 token 生命周期未落地
**问题**：文档称"单次有效 + 15 分钟过期"，但 D1 Schema 无对应表/列，单次生效（防重放）无实现依据。
**影响**：token 被截获可重放登录；过期后仍能用。
**建议**：新增 `magic_tokens(id, user_id, token_hash, expires_at, used_at)` 表；仅存哈希；校验时原子置 `used_at`；过期即拒。

### P0-5 · JWT 无吊销机制
**问题**：JWT 由 `JWT_SECRET` 签名、7 天有效。一旦泄露或需封禁某用户，只能**轮换全局密钥**——代价是全体用户强制下线。
**影响**：无法精准吊销单个会话；安全事件处置粗糙。
**建议**：
- `users` 增加 `token_version`（整数）；JWT 载荷含 `ver`，校验时比对。封禁/登出 = `version++`，无需动密钥。
- 或引入 `sessions(id, user_id, jti, expired_at)` 表，登出删记录，校验查表。

### P0-6 · PII（邮箱）合规与数据主体权利缺失
**问题**：邮箱属个人数据。文档无隐私告知、留存期限、删除/导出通道。
**影响**：触及《个人信息保护法》等合规要求，企业场景不可接受。
**建议**：
- 站点增加隐私政策链接；注册即视为同意。
- 提供 `DELETE /api/me`：级联清除 `users` + `applications` + 其 `magic_tokens`/会话。
- 明确留存期（如账号 2 年 inactive 自动清理），写入隐私政策。

### P0-7 · 密钥轮换流程未定义
**问题**：`JWT_SECRET` / `FEISHU_WEBHOOK` / `EMAIL_API_KEY` 均为环境变量，但无轮换(rotation)与泄露处置流程。
**影响**：密钥长期不变，泄露面随时间放大；泄露后无标准处置 SOP。
**建议**：
- 文档补充轮换步骤：`JWT_SECRET` 轮换配合 `token_version`（先升 version 再换密钥，避免误杀）；Webhook/邮件 Key 支持双密钥并行期。
- 密钥存于 Cloudflare 环境变量（加密静止），禁止出现在代码/Git/聊天记录（参见对话中 PAT token 泄露教训）。

## 3. P1 — 重要缺口（规模化前闭环）

### P1-1 · KV 限流的最终一致性
**问题**：KV 全球最终一致，跨区读后写可能读到旧计数 → 限流或偏松或偏严。
**建议**：对安全敏感限流，改用 D1 计数（强一致）或接受近似并设更严阈值；限流为"尽力防御"而非绝对。

### P1-2 · 可观测性(Observability)空白
**问题**：无错误日志、无告警、无健康检查。Worker/D1 异常时站长被动发现。
**建议**：
- 接入 Workers Logs 或 Sentry，记录 auth 失败/异常。
- 对 `/api/me` 做外部 uptime 探活；auth 失败率突增告警。
- 关键事件（申请提交、审批变更）写结构化日志。

### P1-3 · 内容真源(Source of Truth)策略模糊
**问题**：Git JSON 与 D1 内容并存，未明确哪方为权威、如何防漂移。
**建议**：明确 **Git 为唯一真源**；D1 是构建期派生物；重迁脚本幂等；文档标注"改内容走 Git，不直改 D1"。

### P1-4 · 审批审计链缺失
**问题**：`applications` 仅 `created_at`，无审批人/时间/IP。企业问责(问责制)要求可追溯。
**建议**：加 `approved_by` / `approved_at` / `approved_ip`；审批动作写审计日志。

### P1-5 · 输入校验不充分
**问题**：申请 `note` 未限长/过滤控制字符；邮箱格式仅前端校验。
**建议**：后端 RFC 5322 轻量校验；`note` 限长 500、剥控制字符（防日志注入/存储滥用）；所有写接口拒绝超长。

### P1-6 · 测试策略缺失
**问题**：无单元/集成/压测计划，auth 与门禁逻辑出错即安全漏洞。
**建议**：
- 单元：JWT 签验、魔法链接单次/过期、密码less 流程。
- 集成：6 种访问矩阵（匿名/注册/审批 × 公开/受限章）全量覆盖。
- 压测：限流阈值、D1 并发读。

## 4. P2 — 改进建议（持续打磨）

### P2-1 · 魔法链接 UX 韧性
邮件进垃圾箱 / 跨设备点击失效。建议：邮件发送失败时回退展示一次性短码；落地页明确"链接 15 分钟有效、仅一次使用"。

### P2-2 · WAF 与机器人防护
启用 Cloudflare Bot Fight Mode / 托管规则，对 `/api/*` 加自定义规则（如异常 UA 拦截）。

### P2-3 · D1 容量天花板
免费档 10 万行 / 5GB，当前远未触及；文档标注升级路径（付费档或拆分）。

### P2-4 · 发信域名信誉
自管发信域名需配 SPF/DKIM/DMARC，否则魔法链接易进 spam；建议用 Resend 等托管发信降低门槛。
