## 0. 自审方法

对 V2.0 设计稿执行 **3 轮独立视角自审**，每轮由不同角色透镜切入，刻意寻找可推翻设计的缺陷：

| 轮次 | 透视角色 | 核心质疑 |
|------|----------|----------|
| 第 1 轮 | 安全架构师 | 凭证如何下发/携带？跨域边界在哪？CSRF 面多大？ |
| 第 2 轮 | 可靠性/数据工程师 | 故障模式有哪些？模型是否冗余？吊销是否精准？ |
| 第 3 轮 | 合规/可运维负责人 | 出事如何不瘫痪全站？PII 是否合规？如何灰度回滚？ |

每轮结论：发现缺陷 → 修订设计 → 记录残留风险 → 确认是否阻断实施。

---

## 第 1 轮 · 安全架构自审

**透视**：攻击面、凭证生命周期、CSRF/CORS 边界。

**发现（致命）**：V1.0 采用「独立 Workers 子域（`api.xxx.workers.dev`）+ 跨域 CORS + `SameSite=Strict` cookie」。浏览器在跨站 `fetch` 场景下**不会携带** `SameSite=Strict` cookie → 登录态永远不成立，鉴权链路从根上断裂；若降级为 `SameSite=None` 又需显式 `Access-Control-Allow-Credentials` 与精确 `Allow-Origin`，跨域 cookie 面显著放大 CSRF 风险。

**处置**：API 由独立子域**迁移至同域 Pages Functions**（`vehicle-test-site.pages.dev/api/*`），与 SPA 同源。
- 同源 `fetch` 自动携带 `SameSite=Lax` cookie，无需跨域 CORS。
- 保留 `X-Requested-With: fetch` 头校验作为纵深防御（跨站脚本无法伪造同源头）。
- 更新 §2 架构图与 §5.1。

**残留风险**：无。`SameSite=Lax` + 同源 + 头校验三重约束，CSRF 面收敛到与同域一类。

---

## 第 2 轮 · 可靠性与数据模型自审

**透视**：故障模式、模型冗余、吊销精准度。

**发现（重要）**：V1.0 同时设计 `sessions(id,user_id,jti,expired_at)` 表与 `users.token_version`。两者功能重叠——吊销既可通过 `sessions` 删记录，又可通过 `token_version++`。引入 `sessions` 表增加写入路径、清理定时任务与攻击面，却无额外收益（无多设备独立吊销需求）。

**处置**：**删除 `sessions` 表**，仅保留 `token_version` 作无状态精准吊销。
- 封禁/登出 = `UPDATE users SET token_version=token_version+1`，JWT 校验时比对 `ver`，不一致即 401。
- 更新 §3 Schema、§4.1 接口表、§5.3 吊销说明；§12 清单标注「无 sessions 表」。

**残留风险**：无。单字段吊销已覆盖全部精准吊销场景。

## 第 3 轮 · 合规与可运维自审

**透视**：PII 合规、故障爆炸半径、错误泄露、发布安全。

**发现（4 项）**：
1. **无熔断开关**：鉴权系统（D1/Worker）故障时，全站门禁同时失效→要么全锁死、要么需紧急改代码，无运维保底。
2. **错误响应过详**：5xx/异常可能泄露表名/SQL/堆栈，助长探测。
3. **无灰度/回滚 SOP**：Functions 与前端强耦合，一次发布翻车影响全链路。
4. **PII 同意/留存未显式落地**：隐私政策、注册同意勾选、留存期清理仅在评审建议中，未写入设计约束。

**处置**：
- 新增 §5.8 `AUTH_ENABLED` 熔断开关：置 `false` 时 Functions 回退静态公开模式，鉴权故障不瘫痪全站。
- 新增 §5.9 通用错误响应（不泄露内部细节）+ 结构化日志（含 requestId）供告警。
- 新增 §11.1 灰度发布与回滚 SOP（协调发布 + `AUTH_ENABLED=false` 即时止血 + `wrangler rollback`）。
- §1.2/§5.5 显式化隐私政策页、注册同意勾选、`DELETE /api/me` 级联、2 年 inactive 软删留存期。
- §12 安全清单增补熔断/灰度/通用错误项。

**残留风险（已记录为 deliberate trade-off）**：`AUTH_ENABLED=false` 下退化为全公开，属运维保底而非安全设计，文档已明确其定位。
